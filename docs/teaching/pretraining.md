# Teaching guide: Pretraining (experiment 5)

A teacher's companion to the **Pretraining** experiment (`experiments/world-pretrain`). It covers:

- what the class learns;
- how to run the session on this platform;
- what to put on the wall at each point;
- sample classroom conversations with the questions students usually ask.

Everything here is taken from the experiment as it is built, and the numbers are from runs on this server. The model the class trains here is the base model for [Fine-tuning](finetuning.md).

---

## 1. At a glance

| | |
|---|---|
| **Big idea** | A language model is trained on one task only: **predict the next token**. Everything it can do comes from doing that well on a lot of text. |
| **Students will be able to** | explain next-token prediction and what a loss of 1.3 means; turn a corpus into a token stream; size a model and count its cost before training; read a loss curve; tell a starved model from a well-fed one |
| **Steps** | 1 Pack → 2 Size → 3 Train → 4 Evaluate |
| **Comes after** | Tokenizer (exp. 1). Its step 3 run gives the vocabulary |
| **Leads into** | Fine-tuning (exp. 6), and everything after it, which starts from this model |
| **Length** | one 90-minute session on a GPU; two sessions, or much shorter runs, on a CPU-only server (see §3) |
| **Own code** | steps 2, 3 and 4 can be re-implemented by students; step 1 can't |

### The one sentence to leave on the board

> The model is only ever asked "what comes next?". How good it gets depends on **how many tokens it reads, how many of them are new, and how big it is**, in roughly that order at this scale.

The runs on this server tell that story:

- A **1-million-parameter** model that read **4 million fresh tokens** reached a validation loss of **1.00** and already answered **2.5 %** of questions correctly with no fine-tuning.
- A **6.5-million-parameter** model that read **25 million tokens, but from a corpus of only 69 thousand**, reached **1.28** and answered **none** (§6, step 3).

## 2. Background the teacher needs

**Next-token prediction.** The model reads a window of tokens and, at every position, outputs a probability for each token in the vocabulary being next. The loss is the average **cross-entropy**: minus the log of the probability it gave the token that actually came next.

| loss | the model gave the right next token about… | perplexity |
|---|---|---|
| 7.4 | 1 in 1 700 (random, at a 1 700-token vocabulary) | about 1 700 |
| 2.3 | 1 in 10 | 10 |
| 1.0 | 1 in 2.7 | 2.7 |
| 0 | certainty | 1 |

**Perplexity** is `e^loss`: "on average, it's choosing between this many tokens". The first evaluation of an untrained model on this server showed a loss of **7.46**, about `ln(1 699)`: exactly a uniform guess over the vocabulary. That's a lovely sanity check to show students.

**The corpus.** By default the documents are generated by the course's "world", in three kinds, mixed by the student:

| kind (default share) | example |
|---|---|
| story (55 %) | "After bright sun, Zara and Milo carried a glass jar from the bakery to the house. After a dry wind…" |
| worked problem (30 %) | "What is 29 − 27 + 20? / First 29 − 27 = 2. / Then 2 + 20 = 22. / The answer is 22. / Answer: 22" |
| record (the rest) | "Ruth lives near the archive. / Yara has 13 jars. / Rafi keeps a copper kettle at the boatyard." |

The worked problems matter later: they're why a well-trained *base* model can already answer some questions (step 4), and what fine-tuning builds on.

A teacher can also prepare a real corpus: TinyStories, WikiText-103, Cosmopedia or FineWeb-Edu, under `materials/datasets`. The tokenizer can come from a prepared model too (e.g. GPT-2's); only its vocabulary is borrowed, never its weights.

**The model.** `MiniLM` is a small decoder-only transformer:

- rotary position embeddings (RoPE);
- a SwiGLU MLP;
- RMS-style norms;
- tied input and output embeddings.

| preset | shape (layers × heads × width × context) | parameters (at a ~1.7k vocabulary) |
|---|---|---|
| tiny | 6 × 6 × 288 × 256 | ~6.5 M |
| small | 8 × 8 × 512 × 512 | ~26 M |
| medium | 12 × 12 × 768 × 512 | ~90 M |
| large | 16 × 16 × 1024 × 1024 | ~200 M |
| custom | anything the student picks | — |

**Tokens per parameter.** The rule of thumb in step 2 is that a compute-optimal run reads about **20 tokens per parameter** (the "Chinchilla" ratio). Below about 10 the model is still improving when you stop. Far above 20 on a small corpus, it's re-reading text it has already fitted.

**The training loop.** It uses AdamW with linear warmup then cosine decay to 10 % of the peak, gradient clipping at 1.0, and bf16 autocast on a GPU. It evaluates train and validation loss every `eval_every` steps and **saves the best validation checkpoint**, so stopping early keeps the best model, not the last.

On a CPU, the loop splits each batch into parts that fit the machine's memory and adds the gradients up before each update, so a step is the same step, just slower.

## 3. Before the class

### Checklist

- [ ] Every student has a finished **Tokenizer step 3** run. If not, choose a prepared model's tokenizer on the class's start materials.
- [ ] Open the class for **Pretraining** on the Class page, and set the start materials.
- [ ] Check the wall: screens 1–4 follow steps 1–4, and screen 5 shows the hardware dashboard or the leaderboard.
- [ ] Decide the preset and the number of steps from the timings below, **before** students press Run.

### How long runs take

Throughput measured on this server's CPU worker: **about 14 000 tokens/s** for a ~1 M-parameter model, and **about 3 000 tokens/s** for the tiny preset (6.5 M). A GPU is many times faster.

**Tokens per step** = sequences per step × context length × accumulation. The defaults are 32 × 512 × 1 = 16 384.

| run | GPU (estimate) | CPU-only server (1 slot, 3 GB), measured here where a number is given |
|---|---|---|
| Step 1 Pack, 200 000 generated documents (about 11 M tokens) | about a minute | a few minutes |
| Step 2 Size | seconds, anywhere; nothing trains | seconds |
| Step 3 Train, tiny preset, 3 000 steps at context 512 | tens of minutes | **4–5 h** |
| Step 3 Train, tiny preset, 300 steps at context 256 | a few minutes | **about 15 min** |
| Step 3 Train, a custom ~1 M model, 1 000 steps at context 128 | about a minute | **5 min** (measured: 295 s) |
| Step 4 Evaluate (50 validation batches, 200 questions) | a minute or two | several minutes |

A run measured on this server: the tiny preset, 3 000 steps, 24.6 M tokens, **2 h 10 min** on the CPU worker.

On a CPU server, one run goes at a time, so plan one of these:

1. **The front-of-room run.** You train once at the front with a small model and few steps, and put it on screen 3 as "a student's run, live". Students run their own copies afterwards or overnight.
2. **Tiny and short for everyone.** Tiny preset, context 256, 200–300 steps. It's enough to see the loss fall from 7.4 to under 2 and the curve bend.

**Pack enough data.** The default of 200 000 generated documents gives about 11 M training tokens, fine for tiny. Very small packs (a few thousand documents) make the model re-read the same text hundreds of times. See run 151 in §6.

## 5. The hook (10 min)

Write a sentence on the board and stop before the last word:

> "Zara and Milo carried a glass jar from the bakery to the ___"

> **Teacher:** What comes next?
>
> **Student A:** House? Market?
>
> **Teacher:** How did you know it wasn't "purple" or "seven"?
>
> **Student B:** Because it has to be a place. And we've seen that kind of sentence before.
>
> **Teacher:** That's the whole of pretraining. We show a model billions of "what comes next?" questions, one token at a time, and it gets a little better at guessing each time. It's never told grammar, or facts, or arithmetic. Anything it learns, it learns because it helps guess the next token.
>
> **Student C:** So how can guessing words teach it maths?
>
> **Teacher:** Hold that question. If the text contains "29 − 27 = 2" often enough, the cheapest way to guess the "2" is to actually work out 29 − 27. We'll check in step 4 whether ours learned any of that.

## 6. The four steps

### Step 1 — Pack: turn the corpus into a token stream

**What students set:**

- the tokenizer: their Tokenizer run, or a prepared model's;
- the language;
- generated or prepared documents, and how many;
- for generated documents, the share of stories against worked problems;
- the token budget, the validation share (default 1 %) and the seed.

**What it does:** encodes every document with the tokenizer, joins them with an end-of-text token into **one flat array**, and keeps the last 1 % as validation. During the run, the live chart shows tokens packed and tokens per document.

**What to show:** a student's results, especially:

- **tokens per document**: about 56 for generated documents, about 257 for WikiText;
- the first few documents decoded back from the stream.

> **Teacher:** The model doesn't see documents. It sees one long list of numbers, like this. Training takes random windows of it.
>
> **Student A:** Then a window can start in one document and end in another?
>
> **Teacher:** Yes. The page says so: a window that straddles two documents teaches the model that unrelated text follows unrelated text. The end-of-text token between them tells it "a new document starts here". At this scale it's cheap and mostly harmless.
>
> **Student B:** Why a different seed from the tokenizer run?
>
> **Teacher:** So the model doesn't train on the exact documents the vocabulary was fitted to. It's a small thing here, but it's the same instinct as not testing on your training data.

**Question to throw out:** *"Our generated documents are about 56 tokens long, WikiText's about 257. Which corpus is easier to predict, and why?"* The generated world repeats a small set of names, places and sentence shapes. WikiText is real prose. The world is far easier, which is why its loss goes so low.

---

### Step 2 — Size: choose the architecture and count the cost

**What students set:** a preset (tiny, small, medium, large) or a custom depth, width and head count; the context length; dropout; and the tokens per optimizer step used for the time estimate.

**What it does:** nothing trains. It works out, in closed form:

- the parameter count;
- where the parameters sit (embedding, attention, MLP, norms);
- the compute-optimal token budget (20 per parameter);
- seconds per step and memory, estimated for one A6000.

**What to show:** the "Parameters by component" donut, and the presets table.

> **Teacher:** Tiny has 6.5 million parameters. How many tokens should it read, by the rule of thumb?
>
> **Student C:** Twenty times that… 130 million.
>
> **Teacher:** Right, and we packed 11 million. So what happens if we train on it for a long time?
>
> **Student D:** It sees the same text again and again?
>
> **Teacher:** Yes. It'll keep improving on the training text, but the validation loss stops following. The page even tells you your tokens per parameter when you run it.
>
> **Student A:** Only 8 % of the parameters are in the embedding. Is that normal?
>
> **Teacher:** It depends on the vocabulary. Ours is tiny, about 1 700 tokens. Take GPT-2's 50 000-token vocabulary and the embedding alone would be about 14 million parameters: more than the rest of a tiny model put together. That's why the sample project says to spend the budget on layers rather than a large vocabulary.

**Own code (step 2):** students can add their own estimates, for example FLOPs for a different MLP ratio, or a memory estimate that includes the activations of their chosen context. Or they can compare three custom shapes of the same parameter count: deep and narrow against shallow and wide.

**A note for you:** step 2's "tokens per optimizer step" (default 131 072) only feeds its time estimate. What step 3 actually uses is sequences × context × accumulation (default 16 384). The two will differ unless the student sets them to match, and the A6000 estimate says nothing about a CPU.

---

### Step 3 — Train: run the loop and watch the loss

**What students set:**

- optimizer steps (default 3 000);
- sequences per step (32) and gradient accumulation (1);
- peak learning rate (8 × 10⁻⁴), warmup (150 steps) and weight decay (0.1);
- how often to evaluate, and on how many batches;
- the seed.

**What to show: screen 3, "a student's run, live".** Pick a student who is running now. The wall shows their status, progress, time left against the time limit, the end of the log, and live charts:

| chart | what to say about it |
|---|---|
| **Loss**: train batch, train and validation | starts near `ln(vocabulary)` (7.4 here) and falls steeply, then slowly; the two measured lines should stay together |
| **Gradient norm** (before clipping) | large and jumpy during warmup, then settles; a late spike is worth a look |
| **Learning rate** | the warmup ramp, then the cosine decay: the schedule we chose, not something the model learns |
| **Speed** (tokens/s) | flat once running; the number behind "time left" |

> **Teacher:** It started at 7.46. Where does that number come from?
>
> **Student B:** Is it… random guessing?
>
> **Teacher:** Exactly: `ln(1 699)`, a uniform guess over our vocabulary. So the very first thing on the curve is a check that the setup is right. If an untrained model started at 2, something would be leaking.
>
> **Student C:** Why does it fall so fast and then crawl?
>
> **Teacher:** The first things to learn are cheap: which tokens are common, which follow which. Those give big drops. The later drops need structure: names that stay consistent through a story, numbers that add up. That takes much longer, for smaller gains.
>
> **Student D:** Why warm up? Why not start at full speed?
>
> **Teacher:** At the start the weights are random and the gradients are wild. A full-size step then can throw the model somewhere it never recovers from. Warmup lets the optimizer's statistics settle first. Look at the gradient-norm chart: that early turbulence is exactly what we're protecting against.

**The two runs from this server: a discussion.** Put their results side by side.

| | run 27 | run 151 |
|---|---|---|
| model | custom, **0.98 M** params | tiny, **6.5 M** params |
| corpus packed | **11.0 M** tokens | **69 thousand** tokens |
| tokens read | 4.1 M (a third of the corpus, all new) | 24.6 M (**the corpus about 350 times over**) |
| time | 5 min | 2 h 10 min |
| best validation loss | **1.00** | 1.28 |
| step 4: answers right before fine-tuning | **2.5 %** | 0 % |

> **Teacher:** The second model is six and a half times bigger and trained for over two hours. Why is it worse?
>
> **Student A:** It only had 69 thousand tokens to learn from. It read the same stuff hundreds of times.
>
> **Teacher:** Yes. Its tokens per parameter was about 0.01, a thousand times below the rule of thumb. Bigger doesn't help if there's nothing new to read. The small model read four million *fresh* tokens and learned more. When you choose between a bigger model and more data at this scale, **more data usually wins.**

**If a run fails, put its live view up.** It shows the reason:

- "killed for using more memory than the machine allows": the batch didn't fit;
- "ran past its time limit": too many steps for the machine.

The progress line shows the time left from the first few steps, so you can see a too-long run coming and cancel it early.

**Own code (step 3):** ideas for students who re-implement it:

- a different schedule (constant, linear decay, a longer warmup);
- a learning-rate sweep, which is the sample project's first "cheap win";
- stopping early when the validation loss stops improving;
- logging an extra curve through the SDK (`progress(…, step=…, my_curve=…)` appears on the wall automatically).

### Step 4 — Evaluate: perplexity, samples, and what it can already do

**What it does:**

1. validation loss and perplexity on the held-out tokens;
2. **loss by position in the context**;
3. free continuations of a few prompts (the student's own, or the corpus's openings);
4. 200 generated questions asked of the base model, with the instruction but **no fine-tuning**, graded by exact match;
5. an optional side-by-side comparison with another training run.

**What to show:**

- the loss-by-position chart;
- the free continuations;
- the "Questions, before any fine-tuning" table.

> **Teacher:** This chart shows the loss at each position in the window. What would it mean if the line went *down* from left to right?
>
> **Student B:** The more text it's seen in the window, the better it guesses?
>
> **Teacher:** Yes: it's *using its context*, not just guessing from the token in front of it. A flat line means the context isn't helping at all.
>
> **Student C:** Ours goes down a bit, then up again at the end.
>
> **Teacher:** A little noise is normal at the edges. What matters is the trend. Now read what it wrote.

Run 152, the starved model from step 3, was asked to continue "Mira has 25 baskets and Ruth has 21 baskets. How many more d…". It wrote:

> "Milo lives near the harbour. Vik keeps a cotton sail at the bakery."

> **Teacher:** Is that good?
>
> **Student D:** It's a real sentence! But it has nothing to do with the question.
>
> **Teacher:** That's a base model in one line. It learned the *style* of our world: its names, its places, its sentence shapes. It didn't learn to answer. It's continuing text, which is all we trained it to do. Fine-tuning is where it learns that a question expects an answer.
>
> **Student A:** And the other model got 2.5 % right with no fine-tuning at all. How?
>
> **Teacher:** Thirty percent of its training documents were worked problems with an "Answer:" line. Seeing the instruction, it sometimes continues the pattern it read. That 2.5 % is the number the fine-tuning experiment starts from, and has to beat.

**If the corpus was prepared (e.g. WikiText):** the questions come from the world generator, which that corpus never contained, so the accuracy should be near 0 %. That doesn't mean training failed; the page says so too. Judge that model by its validation loss and its samples.

**Own code (step 4):** students can add their own measurement, for example:

- sample the same prompt at several temperatures;
- plot loss by position for two runs on one chart;
- measure how often the model closes a document with the end-of-text token.

## 7. The project and how it's graded

Students can also hand in a whole model and training loop:

- `project/model.py` must provide `build_model(config)`, returning a module whose `forward(idx, targets)` gives `(logits, loss)`;
- `project/train.py` trains it and saves `outputs/model.pt` with `{"model_state", "config"}` and the tokenizer path.

The grader loads it, checks the **30 M parameter budget**, packs its own held-out stream from the world (a seed nobody trained on), and measures the validation loss.

| check | points |
|---|---|
| `build_model` exists | 10 |
| within 30 M parameters | 20 |
| validation loss (none at 4.0, full marks at 1.2 or below; the check passes below 3.0) | up to 70 |

The leaderboard ranks validation loss, lowest first. The sample project lists the cheap wins, roughly in order:

1. get the learning rate right;
2. spend the budget on layers rather than a large vocabulary;
3. more tokens rather than a bigger model;
4. keep the context short enough that batches stay large.

## 8. Frequently asked questions

**"What does a loss of 1.28 actually mean?"**
On average, the model gave the correct next token a probability of about `e^−1.28` ≈ 28 %. Equivalently, its perplexity is 3.6: it's as unsure as if choosing among about 3.6 tokens.

**"Can we compare our perplexity with GPT-2's?"**
Not directly. Perplexity is *per token*, and a token means different things in different vocabularies. Ours has ~1 700 short tokens. GPT-2's has 50 000, many of them whole words. Guessing a short token is easier than guessing a whole word. Only compare perplexities measured with the same tokenizer on the same text.

**"Why is the validation loss lower than the train loss sometimes?"**
Each evaluation uses a few random batches, so both numbers are noisy. On the generated world, validation text is also as easy as training text. What matters is that the two lines stay together. If validation rises while training falls, the model is memorising.

**"Why do we save the best checkpoint instead of the last?"**
Because the last isn't always the best. If validation loss turns upward near the end, the last checkpoint is the more memorised one. Saving the best means you can stop at any time and keep the best model so far.

**"Why is our model so small? Real ones have billions of parameters."**
So that one lesson fits in one lesson. Every effect in real pretraining shows up here: the steep start, the slow tail, starved against well-fed data, the value of warmup. And you can see it in minutes instead of weeks.

**"What's the difference between a step and an epoch?"**
A step is one update of the weights, here after 16 384 tokens by default. An epoch is one pass over the whole corpus. Run 27 did a third of an epoch; run 151 did about 350. Pretraining usually aims for about one pass over a very large corpus.

**"Does the tokenizer matter?"**
A lot. It decides the vocabulary size, and so the embedding's share of parameters. It decides how many tokens a document becomes, and so how much text one step covers. And it decides what the loss even measures.

**"Can I train it in Japanese?"**
Yes. Pick a Japanese tokenizer run (or set the language), and the world generates Japanese documents. The same goes for step 4's questions.

**"My run is going to take 5 hours. What do I change?"**
Fewer steps, a shorter context (256 instead of 512 halves the tokens per step), or the tiny preset. The time left in the progress line is accurate after the first minute, so decide then.

## 9. Notes for the teacher: known quirks

These are properties of the experiment as currently built. They're worth knowing so a student's sharp question doesn't catch you out.

1. **Step 2's time estimate uses its own "tokens per step"** (default 131 072) and an A6000. Step 3 uses sequences × context × accumulation (default 16 384). On a CPU, the estimate is far too optimistic.
2. **The validation split is the last 1 % of the stream**, a contiguous tail, not random documents. On the generated world it doesn't matter. On a prepared corpus ordered by topic, the validation text can differ from the training text.
3. **Step 4's questions use a different held-out set from the fine-tuning experiment's.** So "answers right before fine-tuning" here (2.5 % in run 29) won't equal fine-tuning's baseline (5–7 % on this server), which also compares three prompt formats.
4. **Tiny packs lead to heavy repetition.** Run 151's pack held 69 thousand tokens, and 3 000 steps read it about 350 times. Step 2 prints the tokens-per-parameter ratio. Point students to it before they train.
5. **The project's validation loss depends on the student's tokenizer.** The grader measures loss per token with whatever tokenizer the checkpoint names, so a smaller vocabulary gives lower loss on the same text. The leaderboard is fair between students who share a tokenizer. With different ones, compare them with care.
6. **The grader packs its stream from the world generator.** A model trained only on a prepared corpus such as WikiText is graded on text it has never seen the like of, and will score badly.

## 10. Exit ticket

Ask each student to write one line for each:

1. What the model is trained to do, in one sentence, with no mention of "understanding".
2. Their run's tokens per parameter, and whether their model was starved, about right, or re-reading its data.
3. One sign on the loss curve that would make them stop a run early.

### Homework (pick one)

- Train the same tiny model twice, once on 20 000 documents and once on 200 000, with the same number of steps, and compare the validation loss.
- Try three custom shapes with about the same parameter count (deep and narrow, balanced, shallow and wide) and trace which learns fastest.
- Pick two runs of different sizes in step 4's "compare with another training run" and start your own scaling curve.
